## 運用ルール

### TDD サイクル

各タスクは **失敗するテストを書いてから実装する。**
タスクに書かれた「先に書くテスト」がそのままレッドの起点になる。

```
1. 「先に書くテスト」を書く      → 落ちることを確認
2. 通る最小の実装を書く          → 通ることを確認
3. リファクタ                    → テストが通り続けることを確認
4. コミット（1 タスク = 1 コミット以上）
```

### ツールとタスク（mise）

ツールチェーンとタスクは [`mise.toml`](../mise.toml) で管理する。

```
mise install              ツール一式（rust + rustfmt/clippy、cargo-insta）
mise run test             全テスト
mise run test:tinymcf     tinymcf のみ（M0 の作業中はこれ）
mise run snap             insta スナップショットのレビュー
mise run lint             clippy（警告はエラー扱い）
mise run fmt              整形
mise run ci               fmt:check + lint + test。push 前にこれ
```

mise は rust を minimal profile で入れるため、`components = "rustfmt,clippy"` の指定が必須。
JDK は M6（`toolchain build-from-jar`）で必要になった時点で `[tools]` に足す。

### 完了条件（DoD）

タスクは次をすべて満たしたときに完了とする。

- 「先に書くテスト」が通る
- `mise run ci` がグリーン
- 生成物を伴う変更は `insta` スナップショットを更新済み（`mise run snap`）

### コミット粒度

- 1 タスク = 1 コミット以上。複数タスクをまとめない
- Conventional prefix 必須（`feat:` / `fix:` / `refactor:` / `test:` / `chore:` / `docs:` / `perf:` / `ci:`）
- **コミットメッセージに本書のタスク ID（`M2-3` 等）を書かない。** 変更内容を書く

### ブランチ

- `feat/<concrete-name>` 形式。タスク名から具体的な名前を作る
  - 良: `feat/tarjan-scc-analysis` / `feat/execute-context-checking`
  - 悪: `feat/m4` / `feat/milestone-4`

## M0. `tinymcf` — mcfunction インタプリタ

**目的:** 以降すべての TDD の測定器を作る。コンパイラがゼロの状態で単体完成する。

**このマイルストーンの意義** — 測定器が無い状態で TDD を始めると、M1〜M4 のテストが
全部 golden file になり、M5 以降で必ず書き直しになる。ここを飛ばしてはならない。

**完了の判定:** 手書きの `.mcfunction` で書いた階乗・フィボナッチが正しい値を返す。

**仕様:** [`crates/tinymcf/SPEC.md`](../crates/tinymcf/SPEC.md)。
各タスクは**まず該当節を pending から確定させ、それから実装する。**

- [x] **M0-1** crate 雛形と NBT 値表現
  - `crates/tinymcf/src/nbt.rs`。`Compound` は `BTreeMap`（出力とスナップショットの決定性のため）
  - ルートの workspace `Cargo.toml` を作り、CI の `hashFiles` ガードを外した（X-1）
- [x] **M0-2** 実行状態（World）
  - `world.rs`。未宣言 objective はエラー（0 として黙認しない）、未設定 holder は `None`
- [x] **M0-2b** SNBT のパーサとフォーマッタ
  - `snbt.rs`。`parse(v.to_string()) == v` の往復一致で検証。`:` は bare-word に含めない
- [x] **M0-3** NBT パス解析
  - `path.rs`。解決・書き込み・削除。フィルタは部分一致かつ再帰、タグも一致を要求
  - 書き込み時の中間生成はバニラの preferred parent 規則に合わせた（次の step が添字ならリスト）
- [x] **M0-4** コマンド行の字句解析基盤
  - 引数トークナイザ（語・引用文字列・セレクタ・NBT パス・SNBT 値・貪欲な残り）、
    `Command` 列挙、未対応コマンドの `Unknown` フォールバックとディスパッチ骨格
  - **計画変更:** 全コマンドの構文を先に書き切るのをやめ、M0-5〜M0-10 が
    自分のコマンド族の**構文と実行を同時に**足す。構文だけ先行させると振る舞いで
    検証できず、計画が警告している golden file 化そのものになるため
  - `args.rs` の balanced scanner 1 本で、セレクタ・SNBT・引用文字列を 1 語として扱う
  - `command.rs` は現状 `Unknown` のみ。各コマンド族は実行側のタスクで足す
- [x] **M0-5** `scoreboard` コマンドの実行
  - `objectives add/remove`、`players set/get/add/remove/operation/reset`
  - `operation` の全演算子（`=` `+=` `-=` `*=` `/=` `%=` `<` `>` `><`）
  - `interp.rs` に `Outcome`（success / result）と `Interpreter`。**失敗は中断しない**
  - `/=` `%=` は floor 除算（`-7/2 = -4`、`-7%2 = 1`）。Rust の `/` `%` とは違う
  - 書き込み系は欠損スコアを 0 で作る。`get` は作らず失敗する
- [x] **M0-6** `data` コマンドの実行
  - `get`（数値はスケール倍、文字列は長さ、list/compound は要素数）
  - `modify ... set value / set from / set string <src> <start> <end> / append / prepend / insert / merge`
  - `remove`、`merge`
  - **storage 対象のみ実行。** entity / block は構文解析はするが「モデル化していない」と診断して失敗
  - `data get` は文字列に長さを返す（要件定義 §4.4 の「`String::len()` は無料」の前提を実証）
- [x] **M0-7** `function` 呼び出しと `return`
  - 関数は**ロード時にパース**。空行と `#` コメントを落とす
  - `return` は呼び出し元に伝播しない。末尾まで落ちた場合の result は実行コマンド数
  - `maxCommandChainLength`（既定 65536）を実装。暴走再帰がテストを止めない担保でもある
  - 再帰の停止条件テストは `execute if` が要るので M0-8 に置いた
- [x] **M0-8** `execute` の条件と `store`
  - `if` / `unless`（`score` の比較と `matches`、`data`）
  - `store result` / `store success`（`score` / `storage` へ、型とスケール付き）
  - 受け入れ: `execute if score $a obj matches 1..5 run say hi` が構文解析され実行される
  - `store` は条件が落ちた場合も発火して 0 を書く（要件定義 §13 の `Option<T>` の前提）
  - 未設定スコアは条件を偽にするだけでエラーにしない
- [x] **M0-8b** `execute` のエンティティ系（M5 が要る範囲）
  - `as` / `at` / `positioned` / `in` / `if entity` / `if block` / `if predicate`
  - セレクタ文字列 → ハーネスが登録したエンティティ、の스タブ登録簿と実行コンテキスト
  - **M0-8 から分離した理由:** これらは世界のスタブという別設計を必要とし、
    M0 の受け入れ条件（階乗・フィボナッチ）にも M4 までにも要らない。M5 で要る
  - 先に書くテスト: `as` が位置を変えず、`at` だけが変えること
- [x] **M0-9** マクロ関数
  - `function ns:f {..}` / `with storage`、行頭 `$` のマクロ行、`$(name)` 展開
  - マクロ行はロード時にパースできないので**呼び出しごとにパース**する
  - 引数なしでマクロ関数を呼ぶと失敗 → 要件定義 §10.1「`#[tick]` がマクロ関数化したらエラー」を
    コンパイラ側でテストできる根拠になる
- [x] **M0-10** 副作用コマンドのスタブ
  - `Interpreter::effects` に `(name, args)` を順序付きで記録
  - **実際に走ったコマンドだけ記録される**ので、そのままトレースとして使える
- [x] **M0-11** 計測 API
  - `Interpreter::report()` — 総コマンド数・関数別内訳・最大深さ・予算超過
  - 課金規則を仕様に明記（`execute ... run` は execute 自身と実行先の**両方**に課金）
  - **呼び出し深さ上限（既定 256）を追加。** バニラには無い実装上の制限 —
    tinymcf は再帰で呼び出しを辿るので、上限が無いと暴走再帰が native スタックを溢れさせて
    テストプロセスごと落ちる（実際に落ちた）
- [x] **M0-12** 手書き mcfunction の受け入れテスト
  - `tests/acceptance.rs` + `tests/fixtures/*.mcfunction`。階乗・フィボナッチ・
    list の破壊的反復・マクロ経由の実行時添字・コスト計測
  - フィクスチャは**生成コードと同じ書き方**にしてある。コンパイラが吐く形が
    ここで先に実証されている状態を作るため
  - **M0 完了。** 以降 `tinymcf` は測定器として信頼できる

**完了の判定:** `.mwl` → AST → HIR → MIR → `.mcfunction` → `tinymcf` 実行で `say hi` の記録が取れる。

- [x] **M1-1** workspace 構成

- [x] **M1-2** 字句解析

  - **エラーで停止せず収集して継続。** 1 文字の typo が残りのファイルを隠さない

- [x] **M1-8** `mwl build`
  - `driver` が入口側の唯一の I/O、`emit` が出口側の唯一の I/O。間は純粋
  - 構文エラーと名前解決エラーを**1 回のビルドでまとめて**報告する
  - CLI は引数 2 つなので `clap` を入れていない。増えたら入れる
- [x] **M1-9** 縦断統合テスト基盤
  - `crates/mwlc/tests/harness/`。`driver::compile` を純粋関数として切り出し、

  - **以降のすべてのマイルストーンがこのヘルパを使う**
  - `tinymcf` は `mwlc` の **dev-dependency**。独立性テストは `[dependencies]` だけを見るので、
    設計どおりの境界がそのまま守られている
  - debug プロファイルで走らせる — 挿入した行番号コメントが実行を変えないことの証明を兼ねる

## M3. 制御フロー

**完了の判定:** `while` と `break` を使ったループが正しい回数で止まる。

- [x] **M3-1** 構文（`if` / `else` / `while` / `loop` / `break` / `continue` / `return`）
  - 条件は `bool` 必須。**`i32` の 0 / 非 0 は条件にできない**（真偽値化を 2 通りにしない）
  - `if` は文であって式。値を持つ `if` は合流点の設計が要るので M4 と一緒に考える
- [x] **M3-2** 制御フローの表現（HIR → MIR）
  - **MIR にジャンプ命令を入れなかった。** ターゲットにジャンプが無いので、
    辺で繋いだ CFG を持つ意味が無い。制御フローは生成関数とガード付き命令の 2 つで表す
  - 「1 命令 = 1 コマンド」は保たれる（ガード付き命令も 1 行）
- [x] **M3-3** インライン / 切り出しの判定
  - 単文で制御が抜けない `if` はインライン。それ以外は関数に切り出す
  - **条件式は `execute if` に直接埋め込む**（`matches` レンジ含む）。
    レジスタに書いてから読み直すと 2 コマンドかかる
- [x] **M3-4** `#[inline]` / `#[no_inline]`
  - `#[inline]` は成立しない場所（`else` 付き・複文・ループ）ではエラー
- [x] **M3-5** ループの lowering
  - ガード + 本体 + 自己末尾再帰の 1 関数。制御が抜けないループの追加コストはゼロ
- [x] **M3-6** `break` / `continue` / `return` の lowering
  - 制御レジスタ `$<fn>.ctl`（0 通常 / 1 break / 2 continue / 3 return）+ 伝播ガード
  - **`continue` を含む本体だけ別関数に切り出す。** インラインのままだと `continue` の
    `return` がループ関数ごと終わらせてしまう
  - **抜けないブロックでは `$ctl` が 1 度も現れない。** break の無いループに
    break の後始末を払わせない
- [x] **M3-7** 生成関数の命名
  - `<親>/if_0` `<親>/else_0` `<親>/while_0` `<親>/while_0/body`
  - `tests/vertical.rs` に `print_generated_commands`（`--ignored`）を用意。
    lowering を目で確認する用

## M4. 関数と再帰

**完了の判定:** `.mwl` で書いた `fact(5)` が `tinymcf` 上で 120 を返す。

- [x] **M4-1** 引数と戻り値
  - 引数は**呼び出し先のローカルと同じフェイクプレイヤー**に書く。引数は初期値を
    呼び出し側が入れるローカルにすぎない
  - 戻り値はバニラの関数戻り値をそのまま使う。定数なら `return <n>` 1 コマンド
  - **生成ブロックからの `return` は `$<fn>.ret` + 制御レジスタで運ぶ。**
    mcfunction の `return` は自分が書かれた関数しか抜けないため
  - シグネチャを先に集める 2 パス構成。定義順に依存しない
  - 値を返す関数が末尾に到達しうるならエラー（`if`/`else` 両方が返せば OK）
- [x] **M4-2** 呼び出しグラフの構築
  - HIR を走査して呼び出し辺を集める
- [x] **M4-3** Tarjan による SCC 解析
  - **同じ成分内への呼び出しだけ**が再帰。相互再帰も同じ判定で拾える
- [x] **M4-4** 非再帰関数の割り付け
  - 引数の書き込みと `function` だけ。退避も復帰も出てこない（コスト測定テストで固定）
- [x] **M4-5** 再帰関数のスタックフレーム
  - **呼び出し側で退避する。** 呼び出し先の入口では引数がもう上書きされていて手遅れ
  - 退避対象は「値が入っているローカル + それまでに配ったテンポラリ」。
    `let` の途中で呼ぶ場合、その束縛はまだ空なので退避しない（読むとコマンドが失敗する）
  - 生存解析で絞るのは M9-7
- [x] **M4-6** 意味論テスト
  - `fact(5) == 120`、相互再帰、フレームが空に戻ること、短絡の観測
  - **§6.3 の見直しを実施。** 右辺が呼び出しを含むときだけ分岐して本当に短絡させ、
    純粋なら `min`/`max` 1 コマンドのまま

## M5. 実行コンテキスト ★

**目的:** minewell が mcfunction に勝つ最大の理由を実装する。
**ここが動いた時点で「使う価値のある道具」になる。** M6 より優先する。

**完了の判定:** `@s` を要求する関数をコンテキスト無しで呼ぶとコンパイルエラーになる。

- [x] **M5-1** セレクタの字句・構文解析
  - 字句解析器が 1 トークンとして保持（M1-2 で実装済み）。中身はゲームの文法なので触らない
- [x] **M5-2** `Selector` 型（コンパイル時型）
  - `let s = @e[..]` は**コンパイル時の別名**。算術・比較・引数・戻り値に使うとエラー
- [x] **M5-3** `as` / `at` ブロック
  - **`at self` ではなく `at @s`。** `self` は M7 の `impl` レシーバに予約済み（仕様 §3.8）
  - 単文で制御が抜けないブロックはインライン（`execute as <sel> run <cmd>`）
- [x] **M5-4** `for e in sel`
  - `as` のみ適用。位置は動かさない。束縛は本体内で `@s` を意味するコンパイル時別名
  - **`continue` は本体からの `return` そのもの**（本体はエンティティ 1 体につき 1 回）。
    ネストしたブロックからの `continue` だけ制御レジスタ経由で運び、本体先頭で消費する
  - `break` / `return` は本体先頭のガードで「以降のエンティティは即座に戻る」に落ちる。
    `execute as` を途中で止める手段がバニラに無いため。**反復分のコマンドは消えない**
- [x] **M5-5** `#[ctx(...)]` 属性と検査
  - **要求は宣言のみ、推論しない。** 推論だと原因から遠い場所でエラーが出る（仕様 §4.6）
  - `dimension` は入れない。次元を切り替える手段がインタプリタに無く、検査できないため
  - **`#[tick]` / `#[load]` は `#[ctx]` を宣言できない。** function タグは実行者なしで
    呼ぶので、宣言した時点で実行時に黙って何もしないことが確定する
- [x] **M5-6** 診断の質
  - **計画変更:** 要求を宣言制にしたので、不足は常に 1 段で分かる。経路の表示は不要になった
  - 代わりに診断は「何が足りないか」と「`as` で囲む / `#[ctx]` を足す」の両方を示す
- [x] **M5-7** debug ビルドの生存ガード（§6.3）
  - `#[ctx(entity)]` の関数の先頭に `execute unless entity @s run tellraw`。release では出ない
  - コンパイル時に検査できないのは「実行時にエンティティが死んでいる」場合だけなので、
    ガードが見るのもそこだけ
