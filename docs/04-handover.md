## 今どこまで動くか

```rust
struct Arena { #[nbt(rename = "Radius")] radius: f64, name: String, keeper: Option<i32> }

fn area(r: fix<1000>) -> fix<1000> {
    let pi = fix::<1000>(3142);
    return pi * r * r;              // スケール補正は自動
}

fn keeper_of(a: Arena) -> Option<i32> {
    let id = a.keeper?;             // 無ければここで抜ける
    return Some(id * 2);
}

#[load]
fn setup() {
    let arena: Arena = nbt!({ Radius: 8, name: "pit" });   // keeper は書かない = None
    let size = area(fix::<1000>(arena.radius));            // data get ... 1000
    if size > fix::<1000>(200000) { say("a big arena"); }
    if arena.name == "pit" { say("the pit is open"); }
    match keeper_of(arena) {
        Some(id) => { say("has a keeper"); }
        None => { say("nobody minds it"); }
    }
}
```

## 次の作業: M9-3（`raw!` のマクロ昇格）

残り 9 タスク。順番の依存は 2 つだけ:

1. **M9-3 は M9-4（`text!`）の前。** 実行時値の補間という同じ仕組みを使う
2. **M9-5〜M9-7（最適化）は最後。** 意味を変えない変換なので、
   `tinymcf` の実行結果が前後で一致することを回帰テストにできる

### M9-3 に入る前に知っておくこと

**マクロ昇格の型はもう 2 つある。** 新しく発明する必要はない:

- 文字列の連結（仕様 §6.27）— `mw.args.a` / `mw.args.b` に書いてから
  `function <ns>:<親>/concat_0 with storage <ns>:mw mw.args` を呼ぶ。
  補助関数の中身は `$data modify ... set value "$(a)$(b)"` の 1 行
- 実行時添字（仕様 §6.21）— `mw.args.i` に書いて `$... list[$(i)]`

`MIR` 側の道具立て: `macro_helper(kind, inst)` が「本体 1 行だけのマクロ関数」を作り、
`Inst::Macro` が行頭に `$` を付ける。`Inst::CallWithArgs` が `with storage ... mw.args`。
**`raw!` はこの 3 つの組み合わせで書けるはず。**

判断が要るところ:

- **補間の構文**。要件定義 §10.1 は `{X}` と書いている。定数（`{定数名}`）は
  ただの文字列連結で無料、実行時の値は `$(名前)` へ落として昇格
- **`#[tick]` / `#[load]` が昇格したらエラー**（先に書くテスト）。タグから呼ばれる関数は
  引数なしで呼ばれ、マクロ関数を引数なしで呼ぶとバニラが失敗する
  （[`../crates/tinymcf/SPEC.md`](../crates/tinymcf/SPEC.md) §4.5 にモデル化済み）。
  **昇格は伝染しない**ので、エラーになるのは「その関数自身がマクロ行を持つ」ときだけ
- 実行時の値をどう `mw.args` に書くか: score なら
  `execute store result storage <ns>:mw mw.args.<名前> int 1 run scoreboard players get <reg>`、
  storage なら `data modify ... set from ...`。M8-4 と M8-6 で両方の書き方が既にある

### M9-4（`text!`）の下ごしらえ

- 要件定義 §10.3 が形を決めている: 連結のみ、装飾は `TextComponent` の
  コンパイル時メソッドチェーン
- 自動変換の表も §10.3 にある。`i32` / `fix<S>` / `bool` は
  `{"score":{"name":"$v","objective":"<ns>.v"}}`、`String` は
  `{"nbt":"...","storage":"<ns>:mw"}`。**実行時の値でもマクロは要らない** —
  JSON がスコアと storage を直接指せるので、そこが `raw!` との違い
- `TextComponent` はコンパイル時のみの型になる（`Selector` と同じ分類）。
  M9-11 で「コンパイル時の型は引数にもフィールドにも書けない」検査を入れたので、
  そこに乗る

**M9-2 で確定した設計**（仕様 §3.20・§4.21・§6.30）:

- **release は文ごと落とす。** 出力から命令を消すのではなく MIR に降ろさない。
  だから「release に assert が無い」は grep ではなく**コマンド数**で確かめられる
- `debug_assert!` は**パース時に式として読む**。`raw!` のようなトークン列ではないので、
  型検査もそのまま効く
- 報告の場所は emit が span から作る（ソース文字列を持っているのが emit だけ）。
  そのために `command()` が `&Options` を取るようになった
- `mir::lower` は `debug: bool` を取る。emit の `Profile` を mir から参照すると
  依存が逆向きになる

**M9-11 で確定した設計**（仕様 §3.19・§4.20・§6.29）:

- **ビューは値ではない。** `Type::View` はコンパイル時のみで、束縛は場所の別名。
  借用と同じ `place_aliases` に乗り、`let` 自体は文にならない
- **データ命令は `DataRef`（対象 + パス）を持つ。** storage と entity の違いはここだけ
- **スケールはタグが決める。** `fix<S>` が float / double タグなら実数、整数タグなら生の単位。
  storage でも entity でも同じ規則（仕様 §4.16）

**M9-1 で確定した設計**（仕様 §3.18・§4.19・§6.28）:

- **`Some` / `None` はパスの有無。** タグ付き compound にすると、バニラが書いた NBT の
  「欠けているフィールド」を `None` として読めなくなる。ここが設計の要
- そのため **`enum` のジェネリクスは要らなくなった**。`Option<T>` は `Vec<T>` と同じ
  内部化された組み込み型
- **`?` はレジスタに開ける**ので中身は score に載る型に限る。compound は `match` で開ける
- **`match` / `if let` は場所でなくてよい。** `Option` を返す呼び出しは成功フラグと結果の
  2 つで答えるので、compound を照合する `enum` と違って storage に置く必要が無い
- 制御レジスタに `4`（失敗して抜けた）を足した。`3` と同じ経路で伝播する
- **tinymcf: 無いパスの読みは診断を出さない**（SPEC §4.2）。未設定の score が条件を
  偽にするのと同じ。**複数一致は今までどおり診断**

**M8 で確定した設計**（仕様 §3.16〜3.17・§4.14〜4.18・§6.25〜6.27）:

- **`fix<S>` の表現は `i32` と同じ。** 違うのは型だけで、その型がスケールを持つ。
  MIR も emit も fix を知らない — `*` と `/` の補正は HIR で `/ S` を継ぎ足す形で入れた
- **const 引数は型引数の列に `Type::Fix(Scale::Const(n))` として乗る。**
  単相化の表もインスタンス名（`half_fix_1000`）も型引数と同じ仕組みで動く
- **NBT 相互運用型は型がタグそのもの。** だから `#[nbt(byte)] hp: f64` はエラー。
  タグを選びたいフィールドは `i32` か `fix<S>` で持つ
- `is_storage()` の下に `is_compound()` と `is_storage_scalar()` を置いた。
  「storage にある」と「compound である」は M7 まで同じ意味だったが、もう違う
- **文字列の比較は照合**（`execute if data ... {キー:"値"}`）。相手が実行時の文字列なら
  マクロ昇格。**リテラルの部分はマクロの値に直接埋め込む**ので引数が減る
- `nbt!` は書き込み先の型と照合する。接尾辞（`20f`）も小数も書かせない

**まだ効いている落とし穴:**

- **storage に新しく物を置いたら、必ず再帰の退避対象（`live_slots`）に入れること。**
  固定パスを書かず `data_temp()` から採れば自動的に入る。M8-6 で 1 度踏んだ
- 生成する関数名・NBT キーは**小文字**でなければならない（データパックのパス制約）
- コマンドの綴りは `Signature.parts`（木の順）で組み立てる。リテラルと引数は交互に来る
- **`execute … run <cmd>` は 2 コマンド。** ただし `execute store success … if …`（`run` 無し）は
  1 コマンド。コスト表明は必ず生成物を読んでから書く

## エディタ支援（X-6、v1 の中）

順番だけ決めてある。**LSP は要件定義 §19 のとおり v1 後**で、先に来るのはハイライト。

1. **tree-sitter grammar（`.mwl`）を 1 つ書く。** nvim と zed はどちらもこれを指せる。

   リソースロケーション（`minecraft:block.note_block.pling` は 1 トークン、`.` と `-` を含む）、
   セレクタ（`@e[...]` は中身を触らず 1 トークン。`]` は文字列の中に出うる）、
   `fix::<1000>` のターボフィッシュ（`::<` は型引数の位置にしか出ない）
2. **VS Code は TextMate grammar が別に要る。** 同じ字句規則から 2 本目を書く
3. 3 つのプラグインは grammar とファイル関連付け（`.mwl`）とビルドタスクだけ持つ。
   **コンパイラには依存させない** — 依存させた瞬間に版の同期が発生する
4. LSP はその後。`mwlc` は既に span 付きの診断を `Report` で返すので、
   「保存時に診断を出す」だけの LSP は薄い。定義ジャンプと補完はその次

## 積み残し（理由つき）

| 項目 | なぜ後回しか | 予定 |
|---|---|---|
| **宛先駆動の式 lowering** | 呼び出し・算術・`&&`・`return <フィールド>` の結果がテンポラリ経由でコピーされ 1 コマンド余分。散らすと一貫性を失うため 1 変更にまとめる | M9-10 |
| **定数畳み込み** | `fix::<100>(fix::<1000>(1500))` のように**両端が定数の式が 6 コマンド出る**。fix 専用の畳み込みを先に入れると二重になる | M9-5 |
| **再帰で未初期化のテンポラリを退避する** | 再帰関数が `if` の中だけでテンポラリを使うと、書かれていない経路でも退避対象に入り、`scoreboard players get` が失敗して数コマンド無駄になる（結果は正しい）。生存解析が入れば自然に消える | M9-7 |
| **ブロック NBT** | 座標のモデルが要る。`positioned` / `if block` を先送りしているのと同じ理由 | 座標モデルと一緒に |
| **`nbt!` の引数位置での照合** | 期待型を式に配る仕組みが要る。いまは注釈付きの `let` だけ | M9-10 |
| **`match` の控えの省略** | 腕が評価対象を書き換えないと分かれば `mw.tmp` へのコピー 1 コマンドは要らない | M9（最適化） |
| **`v[i].push(x)`**（実行時添字の先） | マクロ 2 回と placeholder が要る。まだ誰も使わない | 必要になった時 |
| **`positioned`/`in`/`if block`/`if predicate`**（tinymcf） | 座標・次元・ブロック・predicate のモデルが要り、まだ誰も使わない | 必要になった時 |
| **`mwl toolchain install`** | 取得先の Release がまだ存在せず、HTTP クライアントを足しても検証できない | X-2 の後 |
| **predicate / loot table の ID 検査** | parser 名が版で揺れる。実物の `commands.json` を見てから | 実データ入手後 |
| **`async`/`trait`/`Result`/ユーザ定義マクロ/借用検査/LSP** | v1 スコープ外。予約語だけ確保済み | v1 後 |

## 実装中に決めた、要件定義に書いていなかったこと

要件定義の「Q&A で決めたこと」からは導けず、実装して初めて必要になった判断。
すべて仕様書に反映済みだが、経緯はここにしかない。

1. **MIR にジャンプ命令を入れない。** ターゲットにジャンプが無いので、辺で繋いだ CFG を
   持つ意味が無い。制御フローは生成関数とガード付き命令の 2 つで表す
2. **制御レジスタは必要なときだけ。** ブロックから制御が抜けないなら `$ctl` は
   1 度も現れない。抜けるかどうかはブロックごとに静的に分かる
3. **`#[ctx]` は宣言のみで推論しない。** 推論だと原因から遠い場所でエラーが出る。
   `raw!` の中身は見えないのでどのみち申告が要る
4. **`at self` ではなく `at @s`。** `self` は M7 の `impl` レシーバに予約済み
5. **`&&`/`||` は右辺が純粋なら短絡させない。** 観測上区別できないので 1 コマンドで済ませる
6. **コマンド引数はコンパイル時の値のみ。** 実行時の値にはマクロ関数が要る（M9）
7. **objective 作成関数 `<ns>:__init` を生成し `minecraft:load` に載せる。**
   objective が無いとバニラが全 `scoreboard` コマンドを拒否するので選択肢が無い
8. **コンパイラにコマンド表を埋め込まない。** 埋め込めば「版非依存」が嘘になる
9. **`fix<S>` の `*` と `/` はどちらも掛けてから割る。** 先に割るとスケールが保とうと
   している桁が消える。代償は `fix<1000>` で絶対値 2 の 21 乗あたりの桁溢れ
10. **`fix<S> + i32` は書けない。** 足すべき値が `1` なのか `S` なのか字面から決まらない。
    倍率としての `*` / `/` だけ混ぜられる
11. **const 引数は `fix<S>` のスケールにしか書けない。** 型としても式の値としても使えない。
    値として読めるようにすると式に定数評価が要り、使い道がまだ無い
12. **範囲式（`a..b`）は `slice` の引数専用。** `Range` という型は作っていない
16. **`debug_assert!` は止まらない。** バニラに実行の中断は無く、`return` で抜けても
    呼び出し元は進む。報告するだけで、値はそのまま流れる。`expect` も同じ
13. **`Option<T>` はパスの有無で表す。** タグ付き compound にすると、バニラの NBT の
    欠けたフィールドを `None` として読めなくなる。**要件定義 §4.2 の `#[nbt(optional)]` は
    入れず**、`hp: Option<i32>` と型に書かせることにした（属性と型の両方に書かせると
    食い違える。M8-3 の「型がタグそのもの」と同じ判断）**←要件定義の更新が要る**
14. **エンティティ NBT はビューにする。** `#[entity] struct` のフィールドが場所になり、
    値としては存在しない。stdlib 関数（要件定義 §9 の `get_data`）にしなかったのは、
    文字列パスでは**タグもスケールも欠損も検査できない**ため（設計原則 2）。
    **要件定義 §4.6 と §9 を更新済み**
15. **`fix<S>` のスケールはタグが決める。** float / double タグなら実数、整数タグなら
    生の単位。「ビューだから実数」にすると同じ型が置き場所で意味を変えてしまう

## 見つけたバグ（同種を繰り返さないために）

いずれも**生成された mcfunction を読んで**、あるいは**大きい例を書いて**見つかった。
単体テストは通っていた。

1. **生成ブロックからの `return` が呼び出し元に届かない。** mcfunction の `return` は
   自分が書かれた関数しか抜けない
2. **制御レジスタが呼び出し間で残る。** 最上位まで届いた `return` はレジスタを 3 のまま残す
3. **退避対象に未初期化のローカルが混ざる。** `let rest = f(n-1);` の途中で退避すると
   まだ空の `rest` を読もうとしてコマンドが失敗する
4. **storage のローカルを score として退避していた。** 存在しないスコアを読んで失敗
5. **`match` の腕が評価対象を書き換えると、後続の腕も走る。** 評価対象を `mw.tmp` に
   控えてから判定するように直した
6. **引数の後ろに来るコマンドのリテラルを前に出していた。** `playsound <sound> master <targets>`
   が `playsound master <sound> <targets>` になっていた
7. **リソースロケーションのパスに `.` を含められなかった。**
8. **`pos!` が `~-1` を読めなかった。** `~` `-` `1` の 3 トークンで、1 つの座標として
   読む必要がある。データパックがいちばん書くオフセットなのに、書くと
   「座標が 3 つ要る」という無関係な診断が出ていた
9. **コンパイル時の型を引数とフィールドに書けてしまっていた。** `fn f(s: Selector)` も
   `struct S { p: Pos }` も通り、MIR で `unreachable!` に落ちていた。
   同じ理由で `let z = @e[...];` もコンパイラを落としていた（今は別名として通る）
10. **文字列の比較をレジスタ経由にしていた。** `execute if data` はそれ自体が条件なので、
   `if` の中では 1 コマンド無駄になっていた。大きい例に書いて生成物を読んで気付いた

**教訓は AGENTS.md の「Things that have already caught people out」に集約してある。**

## 作業の型

```
仕様の該当節を確定させる  →  失敗するテストを書く（落ちるのを見る）
                          →  通す  →  mise run ci && git commit
                          →  03-plan.md のチェックボックスと集計を更新
```

- コミットは 1 タスク 1 コミット。仕様 + 実装 + 進捗更新は同一コミット（AGENTS.md の DoD）
- **`mise run ci && git commit` と繋ぐ。** 並べて書くと CI 失敗でも commit が通る（2 回やった）
- push 前に `mise run ci` の終了ステータスを見る。出力の grep では lint 失敗を見落とす

## 環境

- `mise install` → rust（rustfmt/clippy 込み）と cargo-insta
- `mise run test` / `lint` / `ci` / `snap`
- CI は GitHub Actions（mise-action + `Swatinem/rust-cache`）、push と PR で走る
- toolchain 置き場は `MINEWELL_HOME` で変更可。テストは各自の一時ディレクトリを使う
- 例の toolchain は `examples/toolchains/1.21.4/`（手書きの `commands.json`）。
  手で試すときは `cd examples/arena && MINEWELL_HOME=.. mwl build`

**ローカルの `mise run ci` が通っても CI が落ちることがある。** mise の `rust = "stable"` は
CI では毎回その時点の stable を入れるのに対し、手元は rustup 管理の版を指していることがあり、
**clippy の新しい lint だけ CI で出る**（実際に `question_mark` で 1 回落とした）。
push 後は `gh run list` を見るまでが 1 セット。
